### Database Enhancement Narrative 

**Artifact:** Python CRUD Module 

**Course:** CS 340: Client/Server Development 

Enhancement Database Narrative 
	For this enhancement in Database, the third artifact I have chosen is my Python CRUD module that was made in CS 340 Client/Server Development. I have previously used this project for artifact one for software: the explanation about the project is the same, using Mongo to manage animal records through the CRUD operation. In addition, the goal of the project was to learn how an application communicates with a database and how information is able to be stored, retrieved, modified, and removed. Mostly back-end work. However, when I was reviewing my past work that focuses more on the database, I realized there were many problems such as limited query validation, no custom indexing, limited data-integrity protection, and general error handling. I plan to discuss the areas I made changes and a lot of inputs to make improvements to this database enhancement. I will note again that this milestone had already been improved in the software engineering category; I will not be removing enhancements based on category one and will be building on enhancements, but for the database category side. This will let me preserve improvements such as environment-based database configuration and logging while mainly focusing on how the application interacts with MongoDB. 
	 I selected this artifact for my ePortfolio because I am able to show my experience with Python and MongoDB while continuing to show my growth by improving my past projects, like the CRUD project. The original artifact demonstrated my ability to read, update, and delete database records. Now, my enhanced version implements and evaluates database performance. data integrity, security, and reliability. This showcases my current skills in database design, validation, query management, exception handling, and testing of the overall project. I have improved the artifact by adding an index for ‘animal_id’, query validation, stronger data-integrity checks, query projection, and MongoDB-specific error handling. The index was needed since it helped with efficiency in queries; I did consider using a unique index, but I no longer had access to my original ACC dataset (could not check every existing value was unique). So, I stuck with using a regular index to be on the safe side, which also didn’t affect time and storage as much as a unique index had been known to do. 
	I also created a reusable query_check() method, which prevented empty queries from being used with update and delete operations. This section made me consider and think about the purpose of each CRUD operation. An example is that an empty read can actually retrieve all records, while an empty update or delete could unexpectedly affect the whole collection. This helped me acknowledge that database protection should reflect the risks of what happens in individual operations rather than applying the same rules everywhere. In addition, another improvement was having stronger data integrity, which the program now checks for required fields, data types, negative values, and blank names or breeds. One of the challenges I had doing this was applying this validation to partial updates. The data_check method had actually expected a complete animal record, but if you think about it, the update is usually only to change one field. I solved this by keeping complete-record checks for create() while adding partial checks to update(); it only checks the fields that are being changed. Lastly, I was able to improve the efficiency by adding an optional projection in which the application can request only the fields it needs. Also, I added PyMongo-specific ‘ConnectionFailure and OperationFailure’ handling while having a general exception handler for any unexpected problems. 
I have met my course outcomes from Module One that mainly go toward Course Outcomes Four and Five. To achieve Outcome Four, I used Python, MongoDB, PyMongo, indexing, query validation, projection, error handling, data validation, and testing to enhance my functioning database. And, instead of thinking about whether a database operation worked, I had to think more about whether it was safe, efficient, and reliable. The project overall shows progress toward Outcome Five and how important it is to retain a security mindset. Database credentials will be outside the source code through environment variables, with protection against unrestricted update and delete operations that lessen the possibilities of unintended changes to stored information. Also, data validation prevents the information from reaching the database. While doing this process, I have learned that database security does not only go into protecting credentials, but also protects the integrity and availability of stored data. Lastly, I have been making progress in Outcome Three through the design decisions involved in the enhancement: regular and unique indexing, complete and partial validation, unrestricted reads, and potentially destructive writes. I had a difficult time trying to figure out what the right trade-off was, what would be most efficient, or whether I needed to sacrifice runtime or storage depending on what I would use. 
	One of the biggest challenges I had faced was not having access to the original collection in my local MongoDB environment. I did not want to miss out on testing it, and so I created a separate database_tests.py file and used controlled temporary animal records. With this had allowed me to still test the enhance CRUD operations without having to depend on the original data.  In my testing, I had to create a valid animal, read it with a projection, not allow a negative age, perform a partial update, not accept empty update and delete queries, and delete the temporary record afterward.  Through this, I was able to acknowledge that successful testing does not always mean that an operation should function correctly. For example, in the negative age test, it was successful due to the program rejecting the invalid record. For the empty update and delete test had been working correctly too since the safeguards prevent it from unsafe operations.
	Another challenge I had encountered was wondering how much validation each database operation required. At first, it seemed to make sense to reuse the same validation everywhere, but working through the update operation had shown me that complete documents and partial updates have different requirements. And most of the time, people do not update everything and just need one thing changed; saved time and operations to just change one at a time. This had me learn why database validation must consider the purpose of the operation rather than applying the same rules everywhere. 
	Going through this enhancement, the database changed how I think about its overall development and what is expected. When I first started, I just thought about wanting the CRUD operations to function correctly; it requires so much more thinking, like data integrity, efficiency, security, etc. This enhanced artifact has better my skills and thinking process since it not only shows I can work with MongoDB; I can identify weaknesses in the existing database application, be able to develop solutions, and make design decision to make improvements on the work.
