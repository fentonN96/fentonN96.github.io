**Data Structures, Algorithms, and Problem Solving**

I have definitely learned a lot along the way using algorithms and data structures; it helped me understand the form a code could take and follow that standard so that other developers could understand it. In the beginning coursework for that class, I was mainly not sure about whether I had correctly searched for, stored, or retrieved information. As I went by assignment after assignment, I started thinking differently about what the code could do. I started thinking about how fast can it process information? How the structure be able to handle the data if it needed to upscale? How much memory management is needed? In addition, I had to think about the relationship between the data structure and the algorithm using it. 
When I was working with the C++ Course Planner project, it helped me understand more of that concept. In my original version, the course information was stored inside a vector, and I used linear search. The problem was that when the user search for that course, the search method would check courses one by one till the course found; not ideal if we are trying to save the runtime and be more efficient. So, in my capstone enhancement to improve the methods, I replace the linear search with binary search which would move the search from O(n) behavior toward O (log n). And then another problem occurred where I couldn’t just replace one search function with another – the binary search depends on sorted data. 
Due to that requirement, I also had to sort the course vector by course number and even used a lambda comparator to support the sorting; then used the sorted data with the binary-search function. Now, before this enhancement, I had thought of sorting and searching as more of separate ideas. Doing the C++ Course Planner has helped me understand that depending how the data is organized can actually determine which algorithms can be a proper fit for it. 
This has also helped me understand that depending on how it's designed can come with its trade-offs. The C++ Course Planner has a small number of courses and using a linear search would not affect its return results as much. Although if we wanted to upscale the program, using the linear search would not last and slow it down. The Binary search would allow the search space to continue being divided rather than checking courses one by one. At the same time the binary search had shown it needed a requirement that the data remained sorted. Now I had to evaluate, and consider an algorithm what fit best; it didn’t even need to be the fastest one. The developer would have to take into count the size of the data, how often the operation occurs, what preparation is required, and whether the added complexity provides value. 
I also gained more experience with memory management by replacing a raw pointer with ‘unique_ptr’ and ‘make_unique’. Now, if there was wrong input, or unsuccessful search, I had input validation and exception handling so it would be more predictably. When applying these changes, I started changing my mindset about algorithmic problems as a larger part of the problem rather than isolated functions.

My database knowledge had also grown during this capstone since I had to learn to use different tools/software when one was no longer available. One example is that my CS 340 Python CRUD MongoDB assignment had been done on a preconfigured environment, and so when I returned to work on the artifact, I had to go outside the environment and configure MongoDB locally.  I needed to research and learn about authentication, users, connection information, and environment configuration instead of having everything automatically provided. 
Some of the difficult issues I had were trying to use environment variables. The Python code was loading ‘None’ for the database settings, which caused the connection information to show as ‘mongodb://None:None@None:None’. Then I noticed that the variable names in my .env file had not matched what the Python module expected. After I had fixed those names, the values were still returning None. Finally, I discovered that Visual Studio Code was running the test from a different working directory and therefore was not locating the .env file properly. 
The troubleshooting experience has made me acknowledge that application development includes much more than the main source code. A couple of examples include configuration files, authentication, environment settings, directories, database services, and development tools that affect whether the application functions correctly. 
In the Database enhancement made me have a different mindset on CRUD operations because I first I mainly wanted to create, read, update, and delete to work properly. However, along the way, I wondered: what if those operations receive the wrong information? If an empty read query was empty, it might still receive records. Now, if it were an empty update or delete query, it could cause a huge effect on the database unintentionally. Because of this difference, I implemented safeguards that prevent empty update and delete operations. 
Validation was also quite complicated since I tried to use the ‘data_check’ method for creating a new animal record, as a complete record should have all the required fields. But in an update, it is common to change one value, such as an animal’s age. I did not want to make the operation unnecessarily difficult because it would require the entire record for every update. So, I decided to keep complete validation for create only and only used partial validation during updates. 
I had also worked with database indexing, query validation, projections, PyMongo-specific exception handling, and database testing. I had thought of using a unique index for ‘animal_id’, but I no longer had access to the original AAC dataset from my previous course; I couldn’t even check if every existing value was unique. Instead of guessing about the data I couldn’t check, I used a regular index. That choice taught me that software and database design can often include choosing the safest option based on the information actually available. 
When it came to testing the overall application, it created another challenge since in my C++ Course Planner I did not have the original dataset available in my local MongoDB environment. I did not want to skip database testing, so I created controlled temporary records in ‘database_tests.py’. The testing included: creating a valid record, reading it using projection, rejecting a negative age, completing a partial update, rejecting empty update and delete queries, and then removing the temporary test record. Through this process, I noticed that a successful test does not always mean that the operation succeeds. A test can be successful since the application properly prevents unsafe or invalid operations. 

**Security Mindset**

Security had been another area in the Computer Science program that has evolved my thought process, especially if I wanted to learn more in cybersecurity. When I first encountered implementing security measures, I thought it was just something to add after the main program worked. My later assignments and capstone experience have taught me that security decisions should start at the foundation and throughout to the finishing process of an application; basically, being part of the application design. 
One example involved database credentials in my original Python CRUD and it had contained database information directly in the source that is not good. In the enhanced version, I was able to load configuration through environment variables and have a .env file that contained the real values to keep it outside the public portfolio. This meant that the .env example file would be able to show in public which settings the program requires without exposing credentials. 
However, this connects to even if I had moved the password outside the source code, it would not be enough if the program later prints or logs the password. In my public portfolio, I was preparing by reviewing the source code, test files, dashboards, ZIP packages, and repository copies for exposed credentials. In the process, I found and removed credential-printing statements and hardcoded username and password values from the public dashboard copies. I was able to understand that security needs to be always in development and deployment processes. 
Working with the database in this capstone has helped me define security more thoroughly since it not only means not letting an unauthorized person see the password; it also means protecting the integrity and availability of stored information. If there is a situation of unrestricted update and delete operations, we can use query validation, type checks, and blank-field protection; reduces potential corruption and unintentionally modifying data. 
This included a different security perspective that happened in the C++ Course Planner, where I had to replace the raw pointer with a smart pointer. This was to improve memory management and reduce dependence on manual deletion. And in order to have the program respond more predictably, I needed input validation and exception handling. With all these, having these experiences has helped me develop having a more defensive approach to programming. When I create or review an application, I now think about what could go wrong and how the program should respond. And how to reduce the risks before a problem happens.
